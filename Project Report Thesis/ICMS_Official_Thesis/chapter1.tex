\chapter{Introduction}

\section{Project Background}

\subsection{The Temporal Blind Spot of Audits}
Traditional security auditing relies on manual evidence collection and point-in-time assessments. Organizations compile spreadsheets and static configuration snapshots to satisfy regulatory requirements. This creates temporal blind spots because the security status is never continuously validated. Configuration drift after an audit is common and leaves infrastructure exposed to risk even while it appears technically compliant.

\subsection{The Shift to Continuous Monitoring}
To reduce these risks, the cybersecurity sector has adopted Continuous Controls Monitoring (CCM), which replaces manual sampling with automated control validation \cite{bukhari2021automated}. CCM tools connect directly to the computing environment and assess configurations and audit logs. Automation ties compliance status to the environment's current state rather than a past snapshot. NIST Special Publication 800-53 Revision 5 calls for a shift from periodic control assessments to continuous monitoring \cite{nist80053r5}. ISO/IEC 27001:2022 similarly requires continuous risk assessment within an Information Security Management System (ISMS) \cite{quispe2026enhancing}. Both standards require solutions that connect system data to governance goals. Security Information and Event Management (SIEM) systems provide that data. SIEM engines collect telemetry across the enterprise and convert system events into compliance states. This project builds a mechanism that maps SIEM telemetry to regulatory controls.

\section{Problem Description}

\subsection{Telemetry Correlation Delays}
Converting large volumes of endpoint telemetry to regulatory controls is a practical challenge. SIEM systems generate technical notifications, such as failed SSH logins and file changes, that must be correlated to ISO 27001 or SOC 2 control maps. Manual correlation creates time gaps between events and compliance checks, opening windows of vulnerability. Multiple telemetry feeds can also report conflicting states, and manual processes have no reliable way to reconcile them.

\subsection{Algorithmic Failures in Legacy Systems}
Aggregating compliance metrics across distributed fleets exposes data handling limits in typical GRC systems. Standard relational database implementations are prone to the N+1 problem, where the application issues a separate database query for each security control. This produces a linear $O(N)$ retrieval pattern that degrades as agent counts grow. When response times exceed latency thresholds, the system can no longer support continuous monitoring. The deeper problem is that mapping raw telemetry events to regulatory controls often saturates memory bandwidth at the application level. Without query optimization to load only the necessary parts of relational objects, these systems overload CPU and memory, causing timeouts and data inconsistency. The result is that the system becomes too slow to ingest telemetry at the rate it arrives.

Traditional GRC user interfaces also increase cognitive load for analysts. Static dashboards with poor color palettes lead to alert fatigue. Empirical measurement of alert incidence rates in a Security Operations Center (SOC) shows that many triggered alerts come from benign actions, forcing analysts to wade through noise when triaging events \cite{yang2024true}. This slows incident response and raises organizational risk. Dense data grids with no information hierarchy make signal-to-noise filtering a manual task. Over time, the analyst's sensitivity threshold rises until serious security events are overlooked.
\section{Project Objectives}

The ISCMS platform tackles these technology and operational challenges via four development priorities:

\begin{itemize}
    \item \textbf{Automated Telemetry:} Automate the collection and mapping of Wazuh SIEM telemetry to ISO 27001 and SOC 2. The system queries the Wazuh Manager's Security Configuration Assessment (SCA) module, ingests check results, and maps them to a compliance matrix. A Worst-Case Priority algorithm resolves conflicting evaluations so the compliance dashboard always reflects the worst observed security state.
    \item \textbf{Reduce Latency:} Avoid the N+1 database query problem by leverage $O(1)$ set-based aggregations via the Django ORM. The system applies query annotation and conditional filtering using SQL to ensure that the dashboard will load in less than 200 milliseconds. Mapping SQL filtering and aggregations directly to the relational layer rather than in loops. It pre-calculates fleet-wide compliance scores to reduce data round trips and memory allocations on the application host.
    \item \textbf{Security Infrastructure:} Ensure infrastructure and session security via a Dockerized bridge network and isolated PostgreSQL data tier, and a Django REST Framework Role-Based Access Control and stateless JWT token rotation. The system uses a virtual bridge network to isolate the database so the persistence tier is inaccessible to external networks. This bridges with an Identity and Access Management (IAM) system that employs stateless JSON Web Token (JWT) rotation and custom permission classes.
    \item \textbf{UI/UX Engineering:} Manage alert fatigue using a modern user interface that uses flexible design to replace inflexible tables. The design enables rows to wrap and scale as the view is resized. The system leverages depth and gradient scaling to create interactive security cards over embedded telemetry that organizes raw data for decision-making.
\end{itemize}

\section{Methodology}

\subsection{Agile Development Lifecycle}
The ISCMS platform followed an Agile software development lifecycle. Work began with a literature review and structural analysis of the ISO/IEC 27001:2022 and SOC 2 Type II regulatory frameworks. The development team decomposed governance mandates into technical variables and created a schema that maps operational telemetry to compliance objectives. The team then prototyped the API integration layers, evaluating the Wazuh SCA module's capabilities and designing client connectors to poll and serialize endpoint states without overloading the central SIEM infrastructure.

\subsection{Sandbox Testing and Evaluation}
Development sprints focused on backend architecture and implementation. The team benchmarked database aggregation strategies against synthetic telemetry datasets, which led to the adoption of $O(1)$ set-based query projections that eliminated relational bottlenecks. In the evaluation phase, the platform moved to a containerized deployment model using Docker virtual bridge networks. This isolated environment supported security validation, performance profiling, and stress testing against simulated threats and compliance drift scenarios.

\section{Project Scope}

\subsection{Compliance Framework Boundaries}
The ISCMS platform operates within the ISO/IEC 27001:2022 and SOC 2 Type II compliance frameworks. The scope covers the ingestion and mapping of endpoint security telemetry from the Wazuh Manager's Security Configuration Assessment (SCA) module. The system uses the Wazuh REST API to retrieve check results from active agents and correlate them to governance controls, so the compliance state reflects the actual technical configuration. Authenticated requests to the SCA module retrieve payloads describing the pass or fail status of configuration checks on monitored agents. Each check ID is cross-referenced against the ISCMS seed matrix, which maps technical identifiers to governance controls. This correlation translates technical events into regulatory violations.

\subsection{Technical Implementation Boundaries}
The implementation boundary restricts the system to a containerized Docker ecosystem. This environment uses a private virtual bridge network to facilitate communication between the PostgreSQL database, Redis message broker, Celery workers, and the Django-React application stack. This architecture ensures the data persistence tier remains inaccessible to external networks, which maintains a baseline for storing compliance telemetry and organizational policies. Several operational domains remain outside the project scope. The system does not perform active Incident Response (IR) actions, such as isolating compromised endpoints or terminating malicious processes. The platform does not conduct network packet sniffing or automated remediation of configuration drift. The system evaluates and reports on the compliance state but does not change endpoint configurations; infrastructure remediation remains the responsibility of IT operations teams.

\section{Feasibility Study}

\subsection{Technical and Economic Feasibility}
The ISCMS platform is technically and economically feasible. It uses the open-source Wazuh SIEM ecosystem alongside the Django and React frameworks, and these dependencies can handle telemetry streams at the required scale. Containerizing the stack with Docker decouples the application from the host operating system, so organizations can deploy it on existing infrastructure without specialized hardware. Economically, the platform avoids the costs of proprietary SaaS compliance solutions. The open-source technology stack eliminates recurring licensing fees and vendor lock-in risks, shifting the financial model from high operational expenditure (OpEx) to a maintenance cost.

\subsection{Operational Feasibility}
The interface and automated telemetry mapping reduce the labor hours required for evidence collection in Security Operations Centers (SOC).

\section{Areas of Application}

\subsection{Financial Technology (FinTech)}
The ISCMS platform suits industries with strict data privacy and governance mandates. In Financial Technology (FinTech), where transaction processing and infrastructure scaling outpace point-in-time auditing, the platform provides the assurance regulatory bodies require. FinTech startups processing payment data can use it to maintain adherence to SOC 2 Type II and internal security policies, reducing the risk of financial penalties or license revocation due to configuration drift in cloud environments.

\subsection{Healthcare Sector}
The platform also applies to the Healthcare sector for organizations managing Protected Health Information (PHI). Healthcare organizations validate their infrastructure against frameworks like HIPAA and ISO 27001 to prevent data breaches. The platform automates the translation of technical vulnerabilities into compliance violations, allowing hospital networks to maintain a consistent posture across distributed endpoints. Because the Docker environment keeps all telemetry on the organization's private network, the platform supports entities operating under strict confidentiality requirements.
