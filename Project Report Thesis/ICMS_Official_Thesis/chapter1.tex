\chapter{Introduction}

\section{Project Background}

\subsection{The Temporal Blind Spot of Audits}
Historical security auditing methodologies rely on manual evidence collection and point-in-time assessments. Organizations compile spreadsheets and static configuration snapshots to satisfy regulatory requirements. This introduces temporal blind spots since security status is not continuously validated. Post-audit configuration drift is common and exposes infrastructure to risk while remaining technically compliant.

\subsection{The Shift to Continuous Monitoring}
To reduce these risks, the cybersecurity sector is embracing Continuous Controls Monitoring (CCM). This involves automated control validation instead of manual sampling \cite{bukhari2021automated}. CCM tools connect to the computing environment and assess configurations, audit logs and more. Automation ensures compliance is based on the environment's current state. Today's compliance regulations demand ongoing oversight. NIST Special Publication 800-53 Revision 5 advocates moving from periodic control assessments to continuous monitoring to evaluate system integrity \cite{nist80053r5}. Similarly, ISO/IEC 27001:2022 standards mandate a continuous risk assessment in an Information Security Management System (ISMS) \cite{quispe2026enhancing}. These approaches demand solutions to translate system data to governance goals. Security Information and Event Management (SIEM) systems are the source of data. SIEM engines process systemic telemetry from the enterprise and convert system events into compliance states. Baselines translate reporting to data-driven security. This project introduces a mechanism to translate SIEM telemetry with regulatory controls.

\section{Problem Description}

\subsection{Telemetry Correlation Delays}
Conversion of massive endpoint telemetry to regulatory controls is a practical challenge. SIEM systems have technical notifications, like unsuccessful SSH logins and file changes, which must be correlated to ISO 27001 or SOC 2 control maps. Manual correlation leads to time gaps between events and compliance checks. This opens windows of vulnerability in systems. Multiple telemetry feeds can report conflicting states, requiring reconciliation mechanisms manual processes lack.

\subsection{Algorithmic Failures in Legacy Systems}
Aggregating compliance measures across landscape fleets reveals data handling constraints of typical GRC systems. Typical RDB technology can be vulnerable to the N+1 problem where the application makes a series of database queries for each security control. This design defect contributes to a linear $O(N)$ algorithm for retrieving data, resulting in decreased performance with expanding agent numbers. Slow response times preclude continuous monitoring as rendering delays exceed latency bounds for operational awareness. Legacy system GRC algorithmic challenges are related to the inability to manage large data sets. Mapping raw telemetry events to various regulatory controls often saturates memory bandwidth at the application level. Lacking query optimisation to load only the necessary parts of relational objects, these systems overwhelm CPU and memory capacity, resulting in timeouts and inconsistency. This slowdown stops the evolution from audit to continuous monitoring: the system is too slow to ingest telemetry events.

Traditional GRC user interfaces raise the cognitive workload for analysts. Static dashboards and suboptimal color palettes result in alert fatigue. Real-world measurement of the incidence rate and false positives of alerts in a Security Operations Center (SOC) reports that many triggered alerts result from benign actions, so analysts wade through too much noise when triaging events \cite{yang2024true}. This slows incident response, elevating the risk level of the enterprise. Dense data grids do not have a hierarchy when structuring information, making signal-to-noise filtering a manual process. This rigidity leads to alert fatigue, where the analyst's sensitivity threshold is elevated until serious security exploits are ignored. The lack of dynamic modules presents a threat during security breaches.
\section{Project Objectives}

The ICMS platform tackles these technology and operational challenges via four development priorities:

\begin{itemize}
    \item \textbf{Automated Telemetry:} Automate the collection and mapping of Wazuh SIEM telemetry to ISO 27001 and SOC 2. Conflicting evaluations are resolved with a Worst-Case Priority algorithm. The system queries the Wazuh Manager's Security Configuration Assessment (SCA) module, ingesting check results, and maps them to a compliance matrix. This guarantees the compliance dashboard displays the worst-case security scenario and we'll not miss any non-compliant results.
    \item \textbf{Reduce Latency:} Avoid the N+1 database query problem by leverage $O(1)$ set-based aggregations via the Django ORM. The system applies query annotation and conditional filtering using SQL to ensure that the dashboard will load in less than 200 milliseconds. Mapping SQL filtering and aggregations directly to the relational layer rather than in loops. It pre-calculates fleet-wide compliance scores to reduce data round trips and memory allocations on the application host.
    \item \textbf{Security Infrastructure:} Ensure infrastructure and session security via a Dockerized bridge network and isolated PostgreSQL data tier, and a Django REST Framework Role-Based Access Control and stateless JWT token rotation. The system uses a virtual bridge network to isolate the database so the persistence tier is inaccessible to external networks. This bridges with an Identity and Access Management (IAM) system that employs stateless JSON Web Token (JWT) rotation and custom permission classes.
    \item \textbf{UI/UX Engineering:} Manage alert fatigue using a modern user interface that uses flexible design to replace inflexible tables. The design enables rows to wrap and scale as the view is resized. The system leverages depth and gradient scaling to create interactive security cards over embedded telemetry that organizes raw data for decision-making.
\end{itemize}

\section{Methodology}

\subsection{Agile Development Lifecycle}
The ICMS platform used an Agile software development lifecycle for iterative progression. This approach began with a literature review and structural analysis of the ISO/IEC 27001:2022 and SOC 2 Type II regulatory frameworks. By breaking down governance mandates into technical variables, the development team created a schema that maps operational telemetry to compliance objectives. Following this, the methodology emphasized rapid prototyping of API integration layers. The team evaluated the Wazuh Security Configuration Assessment (SCA) module's capabilities and designed client connectors to poll and serialize endpoint states without overloading the central SIEM infrastructure.

\subsection{Sandbox Testing and Evaluation}
Development sprints focused on the architectural design and implementation of the backend system. The methodology prioritized performance optimization by benchmarking database aggregation strategies against synthetic telemetry datasets. This resulted in the use of $O(1)$ set-based query projections to eliminate relational bottlenecks. In the evaluation phases, the platform moved to a containerized deployment model using Docker virtual bridge networks. This isolated environment allowed the team to perform security validation, performance profiling, and stress testing against simulated threats and compliance drift scenarios. By testing the platform within a sandbox, the methodology ensured the ICMS was resilient before enterprise integration.

\section{Project Scope}

\subsection{Compliance Framework Boundaries}
The ICMS platform operates within the ISO/IEC 27001:2022 and SOC 2 Type II compliance frameworks. The scope includes the ingestion and mapping of endpoint security telemetry from the Wazuh Manager's Security Configuration Assessment (SCA) module. By using the Wazuh REST API, the system retrieves check results from active agents and correlates them to governance controls. This data mapping ensures the compliance state represents the technical environment's configuration. The system initiates authenticated requests to the SCA module to retrieve payloads describing the pass or fail status of configuration checks on monitored agents. Each check ID is cross-referenced against the ICMS seed matrix, which maps technical identifiers to governance controls. This correlation translates technical events into regulatory violations.

\subsection{Technical Implementation Boundaries}
The implementation boundary restricts the system to a containerized Docker ecosystem. This environment uses a private virtual bridge network to facilitate communication between the PostgreSQL database, Redis message broker, Celery workers, and the Django-React application stack. This architecture ensures the data persistence tier remains inaccessible to external networks, which maintains a baseline for storing compliance telemetry and organizational policies. Several operational domains remain outside the project scope. The system does not perform active Incident Response (IR) actions, such as isolating compromised endpoints or terminating malicious processes. The platform does not conduct network packet sniffing or automated remediation of configuration drift. The system evaluates and reports on the compliance state but does not change endpoint configurations; infrastructure remediation remains the responsibility of IT operations teams.

\section{Feasibility Study}

\subsection{Technical and Economic Feasibility}
The ICMS platform is technically and economically feasible. The platform uses the open-source Wazuh SIEM ecosystem alongside the Django and React frameworks, which ensures architectural dependencies can handle telemetry streams. Containerizing the application stack using Docker ensures deployment across different hardware environments. By decoupling the application logic from the host operating system, the system guarantees execution and allows organizations to deploy the solution on existing infrastructure without buying specialized hardware. Economically, the platform reduces costs compared to proprietary Software-as-a-Service (SaaS) compliance solutions. By using an open-source technology stack, the system eliminates recurring licensing fees and vendor lock-in risks. Organizations can achieve continuous controls monitoring using existing open-source SIEM infrastructure, shifting the financial model from high operational expenditure (OpEx) to a maintenance profile.

\subsection{Operational Feasibility}
The interface and automated telemetry mapping reduce the labor hours required for evidence collection, which increases the efficiency of Security Operations Centers (SOC).

\section{Areas of Application}

\subsection{Financial Technology (FinTech)}
The ICMS platform provides continuous monitoring for industries with strict data privacy and governance mandates. In the Financial Technology (FinTech) sector, where transaction processing and infrastructure scaling outpace point-in-time auditing, the platform provides the assurance required by regulatory bodies. FinTech startups processing payment data can use the platform to maintain adherence to SOC 2 Type II and internal security policies, which mitigates the risk of financial penalties or loss of licenses due to configuration drift in cloud environments.

\subsection{Healthcare Sector}
The platform also applies to the Healthcare sector for organizations managing Protected Health Information (PHI). Healthcare organizations validate their infrastructure against frameworks like HIPAA and ISO 27001 to prevent data breaches. The platform automates the translation of technical vulnerabilities into compliance violations, allowing hospital networks to maintain a consistent posture across distributed endpoints. By providing data sovereignty within an isolated Docker environment, the platform ensures operational telemetry remains within the organization's private network, which supports entities operating under confidentiality requirements.
