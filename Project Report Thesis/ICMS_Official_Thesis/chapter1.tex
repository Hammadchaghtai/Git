\section{Project Background}

\subsection{The Temporal Blind Spot of Audits}
Historical security auditing methodologies rely on manual evidence collection and point-in-time assessments. Organizations compile spreadsheets and static configuration snapshots to satisfy regulatory requirements. This approach creates temporal blind spots because the security posture remains unverified between audit cycles. Configuration drift occurs frequently after successful audits, leaving infrastructure vulnerable to exploitation despite maintaining formal compliance status.

\subsection{The Shift to Continuous Monitoring}
The cybersecurity industry addresses these vulnerabilities by moving toward Continuous Controls Monitoring (CCM). This shift replaces manual sampling with automated validation of security controls \cite{bukhari2021automated}. CCM platforms integrate with the technical environment to evaluate configurations, access logs, and system integrity. This automation ensures compliance reflects the current state of the environment instead of a historical record. Modern regulatory mandates require continuous visibility. NIST Special Publication 800-53 Revision 5 calls for a transition from static control assessments to ongoing monitoring to validate system integrity \cite{nist80053r5}. Similarly, the ISO/IEC 27001:2022 standard requires organizations to establish an Information Security Management System (ISMS) that evaluates risks continuously \cite{quispe2026enhancing}. These frameworks require tools that map raw system data to governance objectives. Security Information and Event Management (SIEM) systems provide the data for this architecture. SIEM engines ingest telemetry from the enterprise and translate system events into verifiable compliance states. By establishing baselines, organizations move from reactive reporting to data-driven security management. This project implements a system that bridges the gap between technical SIEM telemetry and regulatory control requirements.

\section{Problem Description}

\subsection{Telemetry Correlation Delays}
Translating large volumes of endpoint telemetry into regulatory frameworks is an operational limitation. SIEM platforms generate technical alerts, such as SSH authentication failures or unauthorized file modifications, which must be correlated against ISO 27001 or SOC 2 control matrices. Manual correlation processes introduce delays between event detection and compliance validation. This creates risk windows where system vulnerabilities remain unaddressed. Concurrent telemetry sources can produce contradictory states, which requires resolution mechanisms that manual workflows cannot provide.

\subsection{Algorithmic Failures in Legacy Systems}
Calculating compliance metrics across distributed fleets exposes data aggregation limits in traditional GRC platforms. Standard relational database implementations often suffer from the N+1 query problem, where the application executes sequential retrieval loops for individual security controls. This architectural flaw imposes a linear $O(N)$ algorithmic complexity on data retrieval, which causes performance to drop as the number of monitored agents increases. High latency prevents continuous monitoring because dashboard rendering times exceed thresholds for operational visibility. The algorithmic limitations of legacy GRC systems stem from their inability to process large datasets quickly. When an organization maps raw telemetry events to multiple regulatory frameworks, application-level iteration often exhausts memory bandwidth. By fetching full relational objects through unoptimized query loops, these systems saturate computational resources, which leads to timeouts and data inconsistency. This performance decay prevents the transition from point-in-time auditing to continuous monitoring because system latency outpaces telemetry ingestion.

Legacy GRC interfaces increase the cognitive load on security analysts. Rigid dashboards and unoptimized color schemes lead to alert fatigue. Empirical measurement of alerts in a live Security Operations Center found that a significant proportion of triggered alerts correspond to benign activity, which forces analysts to process excessive noise during incident triage \cite{yang2024true}. This degrades incident response times and increases organizational risk. High-density data grids lack a visual hierarchy, which forces operators to filter noise from critical signals manually. This structural rigidity induces alert fatigue, where the analyst's sensory threshold increases until critical exploits are overlooked. The absence of adaptive layout modules makes these tools a source of risk during security incidents.

\section{Project Objectives}

The ICMS platform addresses these technical and operational gaps through four engineering objectives:

\begin{itemize}
    \item \textbf{Telemetry Automation:} Automate the ingestion and mapping of Wazuh SIEM telemetry to ISO 27001 and SOC 2 controls. The system uses a Worst-Case Priority algorithm to resolve conflicting evaluations. By polling the Wazuh Manager's Security Configuration Assessment (SCA) module, the platform retrieves check results and correlates them against a compliance matrix. This ensures the compliance dashboard reflects the most conservative security posture and minimizes false-positive reports.
    \item \textbf{Performance Optimization:} Eliminate the N+1 database querying bottleneck by using $O(1)$ set-based aggregations through the Django ORM. The platform uses query annotation and conditional SQL filtering to keep dashboard latency below 200 milliseconds. The system projects SQL constraints and aggregations directly onto the relational layer instead of executing sequential loops. By computing fleet-wide compliance scores internally, the system reduces data transfer overhead and memory pressure on the application server.
    \item \textbf{Security Infrastructure:} Enforce infrastructure and session security through a Dockerized virtual bridge network that isolates the PostgreSQL data tier, combined with custom Django REST Framework Role-Based Access Control and stateless JWT rotation. The platform isolates the database within a private virtual network so the persistence tier remains unreachable from external networks. This isolation pairs with an Identity and Access Management (IAM) layer that uses stateless JSON Web Token (JWT) rotation and custom permission classes.
    \item \textbf{UI/UX Engineering:} Reduce alert fatigue by using a modern frontend that replaces rigid tables with flexible layouts. The interface allows data rows to wrap and scale based on viewport size. The platform uses depth and color scaling to distinguish interactive security cards from background telemetry, which structures raw data for decision support.
\end{itemize}

\section{Methodology}

\subsection{Agile Development Lifecycle}
The ICMS platform used an Agile software development lifecycle for iterative progression. This approach began with a literature review and structural analysis of the ISO/IEC 27001:2022 and SOC 2 Type II regulatory frameworks. By breaking down governance mandates into technical variables, the development team created a schema that maps operational telemetry to compliance objectives. Following this, the methodology emphasized rapid prototyping of API integration layers. The team evaluated the Wazuh Security Configuration Assessment (SCA) module's capabilities and designed client connectors to poll and serialize endpoint states without overloading the central SIEM infrastructure.

\subsection{Sandbox Testing and Evaluation}
Development sprints focused on the architectural design and implementation of the backend system. The methodology prioritized performance optimization by benchmarking database aggregation strategies against synthetic telemetry datasets. This resulted in the use of $O(1)$ set-based query projections to eliminate relational bottlenecks. In the evaluation phases, the platform moved to a containerized deployment model using Docker virtual bridge networks. This isolated environment allowed the team to perform security validation, performance profiling, and stress testing against simulated threats and compliance drift scenarios. By testing the platform within a sandbox, the methodology ensured the ICMS was resilient before enterprise integration.

\section{Project Scope}

\subsection{Compliance Framework Boundaries}
The ICMS platform operates within the ISO/IEC 27001:2022 and SOC 2 Type II compliance frameworks. The scope includes the ingestion and mapping of endpoint security telemetry from the Wazuh Manager's Security Configuration Assessment (SCA) module. By using the Wazuh REST API, the system retrieves check results from active agents and correlates them to governance controls. This data mapping ensures the compliance state represents the technical environment's configuration. The system initiates authenticated requests to the SCA module to retrieve payloads describing the pass or fail status of configuration checks on monitored agents. Each check ID is cross-referenced against the ICMS seed matrix, which maps technical identifiers to governance controls. This correlation translates technical events into regulatory violations.

\subsection{Technical Implementation Boundaries}
The implementation boundary restricts the system to a containerized Docker ecosystem. This environment uses a private virtual bridge network to facilitate communication between the PostgreSQL database, Redis message broker, Celery workers, and the Django-React application stack. This architecture ensures the data persistence tier remains inaccessible to external networks, which maintains a baseline for storing compliance telemetry and organizational policies. Several operational domains remain outside the project scope. The system does not perform active Incident Response (IR) actions, such as isolating compromised endpoints or terminating malicious processes. The platform does not conduct network packet sniffing or automated remediation of configuration drift. The system evaluates and reports on the compliance state but does not change endpoint configurations; infrastructure remediation remains the responsibility of IT operations teams.

\section{Feasibility Study}

\subsection{Technical and Economic Feasibility}
The ICMS platform is technically and economically feasible. The platform uses the open-source Wazuh SIEM ecosystem alongside the Django and React frameworks, which ensures architectural dependencies can handle telemetry streams. Containerizing the application stack using Docker ensures deployment across different hardware environments. By decoupling the application logic from the host operating system, the system guarantees execution and allows organizations to deploy the solution on existing infrastructure without buying specialized hardware. Economically, the platform reduces costs compared to proprietary Software-as-a-Service (SaaS) compliance solutions. By using an open-source technology stack, the system eliminates recurring licensing fees and vendor lock-in risks. Organizations can achieve continuous controls monitoring using existing open-source SIEM infrastructure, shifting the financial model from high operational expenditure (OpEx) to a maintenance profile.

\subsection{Operational Feasibility}
The interface and automated telemetry mapping reduce the labor hours required for evidence collection, which increases the efficiency of Security Operations Centers (SOC).

\section{Areas of Application}

\subsection{Financial Technology (FinTech)}
The ICMS platform provides continuous monitoring for industries with strict data privacy and governance mandates. In the Financial Technology (FinTech) sector, where transaction processing and infrastructure scaling outpace point-in-time auditing, the platform provides the assurance required by regulatory bodies. FinTech startups processing payment data can use the platform to maintain adherence to SOC 2 Type II and internal security policies, which mitigates the risk of financial penalties or loss of licenses due to configuration drift in cloud environments.

\subsection{Healthcare Sector}
The platform also applies to the Healthcare sector for organizations managing Protected Health Information (PHI). Healthcare organizations validate their infrastructure against frameworks like HIPAA and ISO 27001 to prevent data breaches. The platform automates the translation of technical vulnerabilities into compliance violations, allowing hospital networks to maintain a consistent posture across distributed endpoints. By providing data sovereignty within an isolated Docker environment, the platform ensures operational telemetry remains within the organization's private network, which supports entities operating under confidentiality requirements.
