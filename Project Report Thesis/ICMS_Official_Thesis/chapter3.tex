\chapter{Requirement Specification}

\section{Existing System}
Traditional compliance management systems rely on manual spreadsheets and disconnected Software-as-a-Service (SaaS) platforms. Governance teams translate ISO/IEC 27001:2022 regulatory requirements into technical controls using documents distributed between governance and technical teams. This method is susceptible to human error, cannot manage versioning, and does not enforce consistency between frameworks. Manual configuration state management increases administrative and operational workloads.

Existing auditing systems conduct assessments at scheduled intervals, and by the time of review, data from internal systems may be stale. Legacy platforms lack specialized relational constraints, which causes latency when processing telemetry and makes it difficult to resolve vulnerabilities consistently. The reliance on proprietary SaaS architectures also introduces data sovereignty risks, as compliance metrics and configurations are transmitted to public cloud environments.

\section{Proposed System}
The ISCMS platform is a centralized system that addresses the limitations of manual mapping and asynchronous SIEM aggregation. The system uses a multi-tier architecture to separate concerns while keeping compliance tracking within an isolated environment.

\subsection{Technology Stack Selection}
The Django framework provides a backend environment with an integrated Object-Relational Mapper (ORM) and built-in security middleware. The Django ORM allows for performance optimizations like $O(1)$ set-based database aggregations. By using query projections and conditional filtering, the system keeps high-volume telemetry manageable. The Django REST Framework (DRF) adds serialization pipelines and supports authentication methods like stateless JSON Web Token (JWT) rotation.

React 18 and Vite are used to build a Single Page Application (SPA) for data visualization. React's Virtual DOM allows the interface to update compliance states without blocking the browser thread. This keeps the dashboard responsive when rendering large volumes of SIEM alerts. By using native ES modules, Vite enhances the development process by minimizing build times while also supporting older tools.

The key database is PostgreSQL, which is used to give ACID adherence to organizational records. Streaming data from SIEM and automated mapping are concurrently read/written to the database. PostgreSQL guarantees that metrics for compliance are kept right through the use of B-Tree indexing and relational constraints. This meets the criteria of ISO 27001 and SOC 2 audits in which the security controls timelines and history need to be verifiable.

To keep the platform responsive during data-heavy operations, the architecture uses Celery and Redis as an asynchronous layer. This decouples tasks like telemetry synchronization from the main application thread to prevent timeouts. Redis is the message broker that moves task payloads between the web server and the background workers. This model allows the platform to scale its ingestion capacity without slowing down the primary API service.

\subsection{High-Level Architecture}
The Presentation Tier is a React SPA that manages user sessions and provides a monitoring interface. It communicates with the API via JSON payloads over HTTPS. By handling state management and rendering on the client side, the system keeps server resources available for data processing and mapping.

The Application Logic Tier, powered by Django REST Framework, manages compliance tasks. This tier handles the Identity and Access Management (IAM) lifecycle and JWT rotation. The Django ORM manages interactions with the database to enforce integrity and execute query aggregations. Asynchronous tasks use Celery and a Redis-based message broker. The system uses a Pub/Sub model to enqueue synchronization tasks, which allows Celery workers to process telemetry from the external Wazuh SIEM Manager. \subsection{Dockerized Infrastructure and Network Isolation}
A Docker virtual bridge network isolates the database from external environments. By keeping PostgreSQL and Redis on a private, internal network, the architecture ensures they are not accessible to external scans. The system uses Docker volumes to prevent data loss across container restarts. The startup sequence uses health-checks to ensure the platform is resilient during deployment. The configuration ensures the Django API container waits for other services before running migrations or starting the server. \section{Requirements Specification}
Requirement engineering for the ISCMS platform maps regulatory mandates to technical specifications. Translating ISO/IEC 27001:2022 and SOC 2 Type II governance objectives into functional capabilities ensures that the architecture satisfies both compliance and operational constraints. This analysis establishes the foundation for a system that automates telemetry ingestion and data aggregation.

\section{Functional Requirements}
The functional requirements define the capabilities the ISCMS architecture must have to operate:

\begin{itemize}
    \item The system must use a 3-tier Role-Based Access Control (RBAC) model with Time-Based One-Time Password (TOTP) authentication.
    \item The platform must automate the ingestion of security telemetry from the Wazuh SCA module via a REST API.
    \item The system must resolve conflicting telemetry states using a Worst-Case Priority algorithm to ensure data integrity.
    \item The platform must generate compliance reports in PDF format for audit documentation.
    \item The system must provide an interface for managing frameworks, controls, and mapping identifiers.
    \item The application must use a stateless session lifecycle with JSON Web Token (JWT) rotation.
\end{itemize}

\section{Non-Functional Requirements}
The non-functional requirements set the operational constraints and performance thresholds for system reliability:

\begin{itemize}
    \item The system must isolate PostgreSQL and Redis within a private Docker virtual bridge network.
    \item The backend must use $O(1)$ set-based query aggregations to keep dashboard latency below 200 milliseconds.
    \item The system must offload Celery and Redis asynchronous background tasks to ensure UI responsiveness.
    \item The frontend should use a responsive architecture to minimize analyst alert fatigue.
    \item The platform must ensure high availability through task retry and message queuing mechanisms.
    \item The system must keep an audit trail for administrative activity and events of the system.
\end{itemize}

\section{User Requirements}
An effective ISCMS user experience centers on its principal users: the System Administrator and the Security Auditor. The System Administrator requires a control plane to configure the infrastructure without direct database access. They should be able to set synchronization schedules, manage RBAC privileges, and override automated telemetry when needed. These controls need clear visual feedback to indicate what is happening inside the Django ORM.

The Security Auditor uses the platform to assess regulatory compliance. They need a clean view of compliance data without visual clutter. The auditors require an RBAC boundary that grants access to historical logs and PDFs but restricts modification of infrastructure mappings. The dashboard must remain responsive during telemetry ingestion; the React SPA architecture uses techniques like memoization to avoid rendering delays.
