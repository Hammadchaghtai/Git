\chapter{Design}

\section{System Architecture}

I designed the Intelligent Compliance Management System (ICMS) using an N-tier architecture. Separating the frontend, API, background workers, and database means we can scale or debug each piece without taking the whole system down. Figure \ref{fig:tier_architecture} breaks down the four main layers.

\subsection{Client and Presentation Tier}
The frontend is a React 18 Single Page Application (SPA). Moving the rendering logic to the browser keeps the server from getting bogged down. It also means analysts don't have to wait for full page reloads when reviewing compliance alerts.

\subsection{Application and Middleware Tier}
The backend runs on the Django REST Framework. This acts as the main gateway, checking JWTs and enforcing role-based access before running any queries. We route all database traffic through Django to maintain a strict security boundary.

\subsection{Asynchronous Processing Tier}
Pulling thousands of logs from the Wazuh SIEM takes time. If we did this on the main Django thread, the API would hang and time out. Instead, I offloaded these I/O tasks to background Celery workers using Redis as the message broker.

\subsection{Data Persistence Tier}
I chose PostgreSQL 18 for the database because compliance data needs strict ACID guarantees. We use standard relational tables for mapping frameworks to controls, but rely on Postgres's JSONField to store the unstructured SIEM logs.

\section{Design Constraints}

Building the ICMS wasn't just about writing code; I had to work around a few hard technical and environmental limits.

\subsection{Technical Constraints}

For security, the database and Redis broker run inside a private Docker bridge network. I didn't expose their ports to the host machine. If you want data, you have to go through the Django API container.

Integrating with the Wazuh API introduced rate limits and network latency. The Celery workers have to batch and throttle their polling requests. Because of this, the dashboard shows the compliance state at the last successful sync, rather than a true real-time feed.

On the frontend, rendering a massive grid of compliance checks can crash the browser. Trying to load thousands of DOM nodes at once blocks the main thread. I fixed this by using React virtualization so the UI only renders what's actually visible on the screen.

\subsection{Infrastructure and Operational Constraints}

Early on, my partner and I lost access to the university's lab network. We had to pivot to building and testing the entire enterprise architecture from home on our personal laptops.

Running a full Wazuh SIEM manager locally burned through our RAM and crashed our machines. To get around this, we built a distributed home-lab. I dedicated one laptop entirely to running Wazuh, while my partner used his machine for development and as the monitored endpoint. We relied heavily on Git to keep our codebases synced while the heavy infrastructure stayed on the dedicated server.

\section{Design Methodology}

We built the platform iteratively using Agile prototyping. Instead of trying to build everything at once, we broke the system into distinct modules so we could test each domain independently before merging.

The project was divided into four main sprints.

\begin{itemize}
    \item \textbf{Sprint 1 (Prototyping):} We first needed to prove the core concept worked. I set up a basic Django backend and tested the Wazuh API to make sure we could actually pull Security Configuration Assessment (SCA) data.
    
    \item \textbf{Sprint 2 (Core Architecture):} Next, I designed the PostgreSQL database schema to link frameworks to rules. We also locked down the API by implementing JWT authentication and role-based routing.
    
    \item \textbf{Sprint 3 (Asynchronous Telemetry):} Because the SIEM data was too heavy for synchronous requests, I added Celery and Redis. This gave us a background worker fleet to handle ingestion and deduplication.
    
    \item \textbf{Sprint 4 (Frontend \& Visualization):} Finally, we built out the React frontend. This involved rendering the data grids, wiring up the state management, and setting up the backend PDF generator for audit reports.
\end{itemize}

\subsubsection{Asynchronous Telemetry Ingestion}
Figure \ref{fig:activity_sync} shows the async ingestion process. When a sync is triggered, the thread forks. The main thread sends a quick 202 Accepted back to the browser so the user isn't stuck waiting. Meanwhile, the Celery worker hits the Wazuh API. If Wazuh is down, it uses exponential backoff. Once it gets the data, it parses the JSON and updates the database.

\section{External Interfaces}
The ICMS doesn't run in a vacuum. It talks to several external services. This section lists out the protocols and authentication methods I used to keep those connections secure.

\subsection{Wazuh SIEM REST API}
The whole system relies on raw logs coming from the Wazuh Manager. My Celery workers hit the Wazuh REST API over HTTPS. I secured this with Bearer tokens generated by the Wazuh server. We pull down the JSON payloads and validate them against the Django ORM before saving them.

\subsection{SMTP Notification Gateway}
For real-time alerts, the backend constructs HTML emails and fires them off through an external SMTP server over port 587 using STARTTLS. I threw this logic into the async message broker so it wouldn't block the API Gateway.

\subsection{Outbound Webhook Integration}
I also added outbound webhooks so the system can talk to tools like Slack or Microsoft Teams. Whenever a compliance rule breaks, it shoots out an HTTP POST request with the JSON event data. To prevent spoofing, I added an HMAC-SHA256 signature to the headers.
