\chapter{Implementation}

The design phase established the requirements for the ISCMS platform and the relationships between its components. This chapter documents the implementation. Translating the architectural diagrams from Chapter~4 into code required addressing hardware constraints, Docker networking, and the integration of a Python backend, a JavaScript frontend, and an external SIEM on a separate machine. The following sections describe each layer.

Development used consumer-grade hardware in a distributed home-lab setup. The Wazuh SIEM manager operated on a dedicated laptop at a fixed IP address (\url{192.168.100.100}). The backend, frontend, and database stack was containerized on a second machine using Docker Compose. Every service configuration, environment variable, and migration step described here corresponds to the project repository.

When the stack boots, Docker brings up the database and Redis first, waits for their health checks to pass, and only then starts the Django backend. This startup ordering was not optional; without it, the backend would crash on boot trying to run migrations against a database that was not yet accepting connections. The Celery worker and Celery Beat scheduler also depend on the backend image and start only after Redis is confirmed healthy. Wazuh, operating as the SIEM data source, is deployed independently; prior work on ML-augmented Wazuh deployments confirms its suitability as a telemetry engine for configuration assessment workloads \cite{chamkar2025improving}.

\subsection{Presentation Layer Implementation (Frontend)}
The frontend is a React 19 Single Page Application built with Vite 8. Vite was chosen over older toolchains because it uses native ES modules during development, which reduces cold-start times to under 200ms. Routing is handled by React Router v7, which uses a declarative \texttt{<Route>} structure to enforce authentication at the component level.

Every HTTP request to the Django backend uses an Axios instance configured with interceptors. The request interceptor reads the JWT access token from \texttt{localStorage} and appends it as a \texttt{Bearer} header. The response interceptor watches for \texttt{401 Unauthorized} responses; when one occurs, it triggers a token refresh. If the refresh fails, the system clears the session and redirects to the login page. This keeps all token-refresh logic out of individual components.

The UI is styled with Tailwind CSS v4 using a custom \texttt{@theme} token set. Recharts is used for data visualization, including the compliance score gauge and per-framework bar charts. Icon assets are provided by Lucide React. The routing table also enforces RBAC at the frontend level: the \texttt{/manage-admins} route requires the \texttt{super\_admin} role, ensuring the UI access matches the API permissions.

\subsection{Middleware and API Gateway (Backend)}
The backend is a Django 5.1 project with the installed application \texttt{compliance} that holds the models, views, serializers, and management commands. The configuration of the project is located in \texttt{core/settings.py} and the secrets are loaded through \texttt{python-decouple} from a \texttt{.env} file.

Authentication uses \url{django-restframework-simplejwt}. Access tokens are valid for 24 hours, Refresh tokens are valid for 7 days with rotation enabled. If the user has TOTP enabled (via \texttt{pyotp)}, the \texttt{Custom\allowbreak Token\allowbreak Obtain\allowbreak View} will return a \texttt{requires\_\allowbreak 2fa} flag, which means that the access to the tokens will require an additional step of verification.

The DRF ViewSets on standard resources and the custom \texttt{APIView} subclass instances for aggregating on the dashboard and generating PDF reports are included in the \texttt{views.py} for this app. The \texttt{Dashboard\allowbreak Summary\allowbreak View} uses an annotated queryset with \texttt{DISTINCT ON agent\_id} to find the latest scan per agent, then computes compliance counts using Django ORM \texttt{Count()} with \texttt{Q()} filter objects. This optimization processes the results in a single SQL statement.

\subsection{Asynchronous Processing Engine}
Compliance scans involve HTTP polling against the external Wazuh REST API. Running these tasks on the main Django request thread would block the server. Instead, work is dispatched to a Celery worker process in a separate container.

The Celery application is initialized in \url{core/celery.py}. It reads configuration from Django settings and uses \texttt{autodiscover\_tasks()} to locate \url{tasks.py} files. The system uses the \texttt{run\_scheduled\_\allowbreak wazuh\_sync} task in \url{compliance/tasks.py}, which includes a retry policy for API failures. A network error triggers an automatic 60-second backoff and retry.

Redis operates in a separate container and is the message broker and result backend. The Celery Beat scheduler uses the \texttt{Database\allowbreak Scheduler} from \url{django-celery-beat}. Scan frequency is stored in the PostgreSQL database and can be modified through the UI without restarting containers. When a manual scan is triggered, the \url{/api/run-scan/} endpoint returns a \texttt{202 Accepted} response and runs the task in the worker container.

\subsection{Data Persistence Layer}
PostgreSQL 18 is the primary database, running in its own container and accessible to the backend over the Docker bridge network. This network isolation approach, where the persistence tier is bound to a private bridge and never exposed to a host port, is a recognized security pattern for containerized applications \cite{casalicchio2020state}. Django connects via \url{psycopg[binary]} version 3.2. Built-in persistent connection support handles connection reuse.

The schema is managed through Django ORM migrations. The backend container entrypoint script runs \texttt{python manage.py migrate} before starting the server to ensure the schema is current. Initial seed data, including regulatory controls and Wazuh rule mappings, is loaded via a management command that creates the relational records from a structured data file.

Raw Wazuh SCA check data is stored in a \texttt{JSONField} on the \texttt{ScanResult} model. Storing the variable-structure SCA response as JSON preserves the original audit evidence while extracted compliance metrics are stored in relational columns for dashboard rendering. Research into JSON versus column-oriented storage confirms that this hybrid approach provides field-level flexibility without sacrificing the indexing and aggregation benefits of the relational engine \cite{aji2026evaluating}.

\section{System Internal Components}
The internal architecture of the ISCMS platform consists of specialized modules that handle the compliance lifecycle. Identity management, data governance, telemetry ingestion, and reporting are handled by independent units. Partitioning the system this way makes it resilient to external API failures. The following subsections detail each component.

\subsection{Identity and Access Management (IAM) Module}
The \texttt{IAM} module handles authentication and authorization for the ISCMS. A custom identity model extends the core Django user system through a \texttt{UserProfile} entity to provide Role-Based Access Control (RBAC). The module recognizes three roles: Superadmins, who have full system access; Admins, who manage frameworks; and Auditors, who have read-only access to scan results and reports.

Authentication uses a stateless JSON Web Token (JWT) architecture. Upon credential verification, the system issues an access token and a rotating refresh token. For accounts that need stronger security, a two-factor authentication (2FA) layer is integrated using the Time-based One-Time Password (TOTP) algorithm. The IAM module uses a two-step login sequence where the user provides a 2FA code before the backend issues the JWT session. This policy is enforced at the API layer through Django REST Framework permissions and at the presentation layer through React route guards.

\subsection{Governance and Compliance Data Engine}
The \texttt{Governance and Compliance Data Engine} manages the relational mappings needed to translate regulatory requirements into technical controls. The engine stores compliance standards as \texttt{Framework} records. Each framework is divided into \texttt{Control} entities that represent specific security requirements. The engine links these controls to organizational \texttt{Policy} documents through a many-to-many relationship to document how each technical requirement is satisfied.

The engine includes mapping logic that connects security telemetry to regulatory clauses. A \texttt{WazuhMapping} system stores identifiers for Security Configuration Assessment (SCA) rules and ties them to governance controls, so the system can categorize security events into the appropriate compliance category. The engine also implements a risk-scoring algorithm that uses weights and thresholds to calculate compliance percentages. When the security state of a remote endpoint changes, the organizational compliance posture updates accordingly.

\subsection{SIEM Telemetry and Synchronization Module}
The \texttt{SIEM Telemetry and Synchronization Module} is responsible for the ingestion of security data from the Wazuh SIEM manager. Given the volume of security logs and the latency of external API communication, this module is implemented as an asynchronous system. A Celery worker tier handles the execution of synchronization tasks, using Redis as a message broker to queue requests.

The synchronization lifecycle begins with a scheduled polling event via Celery Beat. The module authenticates with the Wazuh REST API and enumerates all active security agents. For each agent, the system fetches SCA scan results as a JSON payload. The module stores the raw logs in a \texttt{JSONField} and extracts pass or fail results. This preserves audit evidence while populating the dashboard with rendered data. The module includes a retry policy to recover from network timeouts and SIEM downtime.

\subsection{Automated Audit and Reporting Module}
The \texttt{Automated Audit and Reporting Module} transforms scan results into audit artifacts. When a report is requested, the module performs an aggregation query across historical scan data, calculates compliance percentages, and identifies gaps where controls have failed. This aggregation is optimized with database-level annotations.

The module creates audit-ready evidence that meets regulatory requirements. A server-side rendering engine converts HTML templates into PDF files. These documents include framework summaries, endpoint status lists, and gap analysis sections. PDF generation runs in the background worker tier so the user interface stays responsive. Files are served through a secure interface, removing the need for temporary storage of sensitive data on the local file system.

\subsection{Frontend State and Visualization Layer}
The \texttt{Frontend State and Visualization Layer} is the interactive interface for the compliance lifecycle. Built as a React Single Page Application (SPA), this layer uses a component-based architecture. A global \texttt{AuthContext} provider manages the client-side session, JWT token persistence, and automatic token refresh logic through Axios interceptors. Outbound API requests are always authenticated, and the user's session stays active without manual intervention.

Data visualization is central to this layer. A specialized charting library renders compliance score gauges, trend lines, and status distributions. These visualizations are driven by data from the backend. The frontend mounts different components depending on the user's RBAC role. An auditor session loads a different set of navigation and dashboard widgets than an administrator session, so users only see the features relevant to them.

These technologies were selected based on the requirements of a security governance platform. The Python/Django stack was chosen for the backend because of its handling of complex relational data and its support for authentication. On the presentation layer, React was used to build a responsive Single Page Application (SPA) that can manage UI states, such as dashboard updates and compliance gauges, without requiring full page reloads.

Before implementation, the system went through an iterative UI/UX design process using Google Stitch. This platform was used for rapid prototyping, developing wireframes and mockups to validate user flows before writing frontend code. This phase set the visual direction and confirmed that navigation for security assessments was intuitive.

The development workflow was AI-driven and centered around the Antigravity integrated development environment. Antigravity served as the orchestration hub, coordinating codebase management with AI modeling. Throughout the project, models such as Claude and Gemini were used for pair-programming tasks, specifically for the Wazuh telemetry parser and the Celery task retry logic. This environment helped debug container networking issues and generate API documentation.

Finally, the academic documentation was managed through LaTeX, MiKTeX, and TikZ. These tools ensured that the report adhered to academic typesetting standards and that architectural diagrams were precise. The TikZ library allowed for the programmatic generation of system topology diagrams.
